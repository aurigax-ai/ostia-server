# Design notes

Why the server is built the way it is. Each entry is a decision someone changing the code should know before reversing it.

## One binary, modules switched in config

`relay`, `publish`, `sync` and `push` share accounts, device keys, rate limits, quotas, storage and the admin commands. A person running a homelab starts one process. A larger deployment can start the same binary with only one module on; the modules talk to each other only through the database.

## The relay passes TLS through

The phone already pins the desktop gateway's certificate fingerprint and ignores the host name. An SNI passthrough relay leaves that handshake untouched, so the relay cannot read or alter the traffic and the pairing check code is unchanged. A relay that terminated TLS would show a different certificate and fail the pin.

The desktop dials out over a WebSocket, so it needs no open port. There is one WebSocket per phone connection and TCP provides the flow control, so there is no multiplexer.

The relay can share the HTTPS port with the API or have a port of its own. `listen.https` is an SNI router that hands relay hosts to the relay and terminates or forwards every other host. `listen.relay` is a second listener that does only the first half: it reads the ClientHello, hands relay hosts to the relay and closes everything else. It exists for deployments where an outer proxy already owns 443, terminates TLS for the API and the share hosts, and passes the relay hosts through untouched to a port of the server's. The phone's TLS then arrives as plain TCP, so the server cannot see the phone's address and needs the proxy to tell it, with PROXY protocol v1 or v2. Only peers in `listen.trusted_proxies` are read for a header, and they must send one: a trusted address that sends none is dropped, and a header from any other address is not parsed and is treated as garbage like any non-TLS bytes, so a client cannot choose its own address or the address it is limited under. The header is read in the connection's own goroutine, on the one deadline that also covers the ClientHello, so a silent trusted peer holds only its own slot of the pending pool and cannot delay the accept loop. A connection takes a slot of the global pool when it is accepted and counts against the per-address cap once its address (from the header, if there is one) is known.

Unknown labels and non-TLS connections are held for the hello timeout and then closed without a reply. A known label with no desktop listening is reset at once. Answering differently would let a scanner tell which desktops exist or are online.

## Shares: one origin each, a fixed shell, the key in the fragment

The key is in the URL fragment, which browsers never send. A fixed shell page fetches the ciphertext, decrypts it with WebCrypto and renders it inside `<iframe sandbox="allow-scripts" srcdoc>`. The limit of every web-delivered end-to-end page applies: a compromised server could serve a different shell that leaks the fragment. Self-hosters trust their own box; the shell is plain unminified JavaScript in `web/share-shell/` so it can be read.

The shell's Content-Security-Policy allows inline scripts and styles (`'unsafe-inline'`). A `srcdoc` frame inherits the embedding page's policy, and the shared artifact is one HTML file with inline script and style, so a policy of `script-src 'self'` would stop every artifact. The shell has no injection point: all shared content lives inside the sandboxed frame, whose opaque origin cannot reach the parent or the fragment.

Public shares go through the same shell: the root of a public share is the shell, never the artifact, and `/blob` returns the bytes as `application/octet-stream` under `sandbox`. Every share, public or encrypted, shows a bar outside the frame ("Shared from Ostia · made by a user, not by Ostia · Report") and, once per share id, an interstitial telling the visitor an Ostia user published the page and not to enter passwords or personal details. The acknowledgement is kept in the shell's `localStorage`, never a cookie.

## Sync blobs are named by their content

The plan for the sync protocol derived a blob id from the path alone. That lets a device overwrite a blob that another device's manifest still points at, and a write that loses the manifest race would leave a manifest whose hash does not match its blob. The id is now `HMAC(pathKey, path || hash)`, blobs are write-once, and a lost race leaves harmless unreferenced blobs that `POST /v1/sync/gc` collects. The server cannot read manifests, so only a client can say which blobs are still referenced.

Key rotation is one transaction (`POST /v1/sync/rotate`): the new manifest and every changed wrap land together, so no device ever sees a manifest it has no wrap for.

## Push registration is a desktop-issued ticket

A phone has no account, so it cannot prove anything itself. The desktop does: a signed-in desktop mints a single-use ticket and gives it to its own phone, which registers with it. The handle is therefore bound to the desktop's account, a stranger cannot fill the table, an account can only hold a few, and only that account's session can ping or delete the handle. A ping has no content, at most one wake-up per 30 seconds per handle.

Each operator uses their own FCM and APNs credentials. Platform tokens are bound to the app build, so a server can only push to phones running a build registered under its credentials. There is no shared push gateway.

## Elevated sessions for destructive actions

The bearer token lives in the desktop's main process for an hour. If it leaks, an attacker must not be able to delete devices, wraps, blobs or the account. Those actions need another signed-in device to approve (the person clicks on that device) or a fresh GitHub sign-in by the same GitHub user. Elevation lasts five minutes and is attached to the session that asked. The approver must also have belonged to the account for a day (longer than a session lives), and adding a device beyond the second is itself elevated, counting open invites: otherwise a stolen token could invite devices of its own and use them to approve each other. The owner can always fight back during that day: an established device removes a device still on probation without elevation, and the last established device cannot be revoked by a token alone. Wraps carry no signature, so an unelevated session may only fill empty wrap slots. Reading the passphrase or recovery wrap, which a thief could try to guess offline, and pushing a manifest, which a thief could use to push real history out of the retained versions, need a device signature like inviting does (see protocol.md). The cost is that an account with a single non-GitHub device cannot do these things itself; the operator can still delete the account from the command line.

## Client addresses behind a proxy

Rate limits key on the client address. Behind a proxy that address is only known from a header, and a header anyone can send is worthless. The server reads the header only from connections whose peer is listed in `listen.trusted_proxies`, and believes exactly one hop: the last address in the header, which the nearest proxy appended. Entries to its left are never read, so a client cannot pick its own key by prepending addresses, not even ones inside the trusted range. Walking past trusted addresses to the first untrusted one was dropped because a caller whose own address is inside the range (another pod, or a pod using the public name) would then hand the server the choice. A caller that reaches the server directly, bypassing the proxy, is still believed if its address is in the range, so the range should list the proxy and the network should only let the proxy in. The limiter tables are capped at 50,000 addresses each: once a table is full, the address that was seen longest ago is dropped to make room, so memory stays bounded and a new client always gets a bucket of its own. In `forward` mode the server tells the proxy the client address with PROXY protocol v2, since it cannot add a header to a TLS stream it does not terminate.

## Request deadlines

The proxy in front may allow an hour of silence, so the server bounds every phase itself: ten seconds for the headers, then each route a deadline set through `http.ResponseController` as it starts, one minute to read the body and one to write the answer for JSON routes, five minutes for routes that carry megabytes (sync blobs, the manifest, rotate and share uploads). `http.Server` carries the five minute limit as the outer bound for what no route narrows, such as share downloads. A connection that trickles a body therefore frees its slot after a minute instead of holding one of the proxy's connections open. WebSocket upgrades hijack the connection, which clears the deadline.

## Relay streams start unconfirmed

A label is an identifier, not a secret: it is in the pairing QR and in every address list. Without a check, anyone who learned it could hold the label's connection slots and burn the owner's byte quota with idle or garbage streams. A stream is therefore unconfirmed until the desktop says its gateway accepted the phone (valid device token or live pairing code). Unconfirmed streams are short lived, capped separately, and unbilled; when the pool is full the oldest unconfirmed stream is evicted so squatters cannot lock out the real phone, and the per-label budget is spent only on confirmed streams. The accept side of the relay never learns what the traffic is; the gateway tells the desktop client, which tells the relay only the stream id.

## Pre-handshake connections are pooled per address

The router holds a connection until its ClientHello arrives, which is a slow-connection attack surface. The pool is capped, each source address (an IPv6 /64 counts as one) may hold only a few places, and when the pool is three quarters full the router stops holding connections that are not TLS.

## The share domain is a sandboxed origin, not a cookie jar

A share can hold script from a stranger, so the question is what that script can reach. Browsers scope cookies by host and by registrable domain, so a page on a sibling host can try to set a cookie for the whole domain (`Domain=example.com`) or read one that was set that way. The server closes that door from both ends instead of requiring a separate registrable domain:

- **Artifact code never runs in a real origin.** Ostia's own shell renders every share (a public one fetches its bytes as is, an encrypted one decrypts them in the browser) as the `srcdoc` of an `<iframe sandbox="allow-scripts">` without `allow-same-origin`, so the artifact has an opaque origin, no cookie jar and no way to reach the shell, its bar or the fragment. A `srcdoc` document inherits the shell's CSP, which allows requests to the share host, so the shell puts a policy of its own at the top of the artifact's `<head>` (`connect-src 'none'`); the two policies add up, and the artifact can neither read the share host nor send to it. Tests fail if the data policy loses the sandbox, if the shell grants `allow-same-origin`, top navigation, popups or forms, if the artifact policy goes missing, or if a share response sets a cookie.
- **A share cannot send the visitor to another host.** The shell's policy has `frame-src 'none'`: a `srcdoc` frame is exempt, but any navigation of it (a script setting `location`, a `<meta http-equiv=refresh>`) is refused, and the frame is left blank. The sandbox has no `allow-top-navigation*`, `allow-popups`, `allow-forms`, `allow-downloads` or `allow-modals`, and the artifact's own policy adds `form-action 'none'` and `base-uri 'none'`. No route on the share host redirects, and the redirects on the API and admin host go to fixed `/admin/...` paths only (every `http.Redirect` was audited); no `Location` header is built from a request. The shell never builds a URL from share content except the one below.
- **Known gaps of the sandbox.** `connect-src 'none'` does not cover WebRTC: an artifact can open an `RTCPeerConnection` to a STUN or TURN server of its choosing, which lets it tell its author that a visitor opened the page and send out whatever the visitor types into it. Browsers also resolve names speculatively (DNS prefetch) in ways no CSP stops. No shipped CSP directive closes either, so the interstitial's warning not to enter passwords or personal details is the mitigation. `Permissions-Policy` denies `picture-in-picture` along with fullscreen and the other powerful features, so no window can float above the bar.
- **Legitimate links go through the shell.** The artifact can ask the shell to open a link with `parent.postMessage({ostiaOpen: url}, '*')`. The shell accepts the message only from its own frame, only for `http:` or `https:` URLs without credentials and up to 2048 characters, and shows its own confirmation outside the frame ("This link leaves the shared page: host") with Open and Cancel. The box is an overlay that does not move the frame, shows the registrable domain in bold and cuts a long subdomain in the middle (the full host is in its tooltip), keeps Open disabled for one second, and ignores further messages while it is open, so a layout shift or a swapped link cannot turn a visitor's click into an Open. Open calls `window.open(url, '_blank', 'noopener,noreferrer')` from the click.
- **Every cookie the server sets is host-only.** None carries a `Domain` attribute, so the browser sends it to the one host that set it and nowhere else. The admin session cookie is `__Host-ostia_admin` (`Secure; Path=/`, no `Domain`): the browser refuses to let any other host, including a sibling under the same registrable domain, set or overwrite a cookie with that prefix. The sign-in state cookie was already `__Host-`.
- **The shell is first-party code.** It runs in a real origin (`<id>.<share>`), served from the share host with nothing but static files and the three routes of a share. It holds no session and no token, and the admin UI and the API do not exist on that host.

The API's own defences do not depend on the share domain: every state-changing admin request needs a session-bound CSRF token and a same-origin request (`Sec-Fetch-Site: same-origin`, or an `Origin` equal to the API's; `Origin: null`, which a sandboxed page sends, is refused), the API uses bearer tokens, and the admin cannot be framed. What a same-zone layout does depend on is browser behaviour for *other* services under the same registrable domain. Under the cookie specification's wording a sandboxed document's "site for cookies" comes from its URL, not its opaque origin, so a browser that follows it would treat a share as same-site with every host under the domain and send `SameSite=Lax` and `Strict` cookies on its requests; Chromium treats it as cross-site, and the behaviour of other browsers is not verified. Do not run anything on the registrable domain that relies on `SameSite` alone as its CSRF defence, and prefer a separate registrable domain if you do. With that caveat, the share domain gives a malicious share nothing it could use against this server, so the server only refuses what would put the shares at or above the API: the same host, or a parent of it (`example.com` for `api.example.com`). Use a dedicated zone: API `sync.ostia.example.com`, shares `share.ostia.example.com`, each share at `<id>.share.ostia.example.com`, with its own wildcard certificate and DNS record. Do not put shares on a parent, because a share host would then be a sibling of everything beneath it and a parent-domain cookie from any other service would reach it. A separate registrable domain (or a public suffix such as `github.io`) is still the stronger choice where the operator controls one, since it also isolates the browser's other per-site state; the sandbox is what the same-site layout relies on.

## Rate limits and authentication on every route

Public routes (sign-in, challenge, reports, push registration and ping, share hosts, `/v1/info`, `/healthz`) have per-address limiters. Every other route needs a bearer token and is limited per device. Share deletion is authorised by the delete token or the owner's bearer and is limited per address.\n\n`docs/openapi.json` states the security of every route. `internal/server/openapi_test.go` fails when the document and the registered routes differ, when a route marked as authenticated answers an anonymous or invalid bearer with anything but 401, and when a route marked as public is not rate limited. Adding a route means deciding both in the document.

## No access logs

Request logs would hold addresses and share ids. The server logs start-up and errors, never successful requests. Rate-limit state is in memory only.
